# 自动大文件流式加密/解密与进度条需求文档

## 1. 背景

当前项目已经在 `crypto.rs` 中提供了 AES-256-GCM 和 ChaCha20-Poly1305 的流式加密、解密底层函数，也在 `compression.rs` 中提供了流式压缩、解压缩函数，并在 `cli.rs` 中提供了基础进度条输出函数。

但当前主流程中的 `file_handler::encrypt_file` 和 `file_handler::decrypt_file` 仍然会通过 `read_to_end` 将整个文件读入内存后再处理。`app.rs` 在解密后还会读取整个临时明文文件，用于判断是否为目录归档。因此，现有命令行加密、解密流程不会自动根据文件大小切换到流式处理。

本需求要求将流式能力接入正式文件加密、解密流程，实现自动判断大文件、自动选择流式路径，并在加密和解密过程中显示进度条。

## 2. 功能目标

- 自动判断输入文件大小，超过阈值时使用流式加密。
- 自动识别加密文件是否采用流式格式，解密时使用对应的流式解密路径。
- 小文件保持现有整体读入内存的处理路径，避免不必要的格式变化和实现复杂度。
- 加密和解密都显示字节级进度条。
- 进度条默认在交互式终端显示，在非交互输出或管道环境中不污染 stdout。
- 加密文件格式需要能可靠记录流式处理所需元数据。
- 保持对现有非流式加密文件的向后兼容。
- 明确目录加密、压缩、错误恢复和测试验收要求。

## 3. 非目标

第一版不要求完成以下能力：

- 不要求所有算法都支持流式处理。
- 不要求 RSA-OAEP 和 ECIES-P256 直接支持大文件流式加密；它们应继续走现有混合加密或文件加密限制。
- 不要求目录归档格式本身完全流式化；目录加密可以先继续生成临时归档文件，再对归档文件按大小自动选择流式或非流式加密。
- 不要求跨进程断点续传。
- 不要求 GUI 进度条。
- 不要求并行分块加密。

## 4. 术语

- 小文件：文件大小小于流式阈值的普通文件。
- 大文件：文件大小大于或等于流式阈值的普通文件。
- 流式阈值：判断是否启用流式加密的最小文件大小。
- 流式文件：使用分块加密格式写出的加密文件。
- 非流式文件：使用当前整体加密格式写出的加密文件。
- 处理进度：已经从输入读取、加密、解密、压缩、解压缩或写出的字节进度。

## 5. 默认行为

### 5.1 加密

加密单个普通文件时，程序应先读取文件元数据，获取原始文件大小。

默认规则：

- 文件大小小于 `STREAMING_THRESHOLD` 时，继续使用现有非流式加密流程。
- 文件大小大于或等于 `STREAMING_THRESHOLD` 时，自动使用流式加密流程。
- 默认 `STREAMING_THRESHOLD` 建议为 `64 MiB`。
- 阈值需要集中定义，不能散落在业务代码中。
- 阈值应允许后续通过配置或 CLI 参数覆盖，但第一版可以只提供内部常量。

空文件处理：

- 空文件应继续可加密、可解密。
- 空文件可走非流式路径，也可走流式路径，但行为必须稳定且有测试覆盖。

### 5.2 解密

解密时不能根据当前密文文件大小决定流式或非流式路径，而必须读取加密文件头中的格式标记。

默认规则：

- 如果文件头标记为非流式，使用现有非流式解密路径。
- 如果文件头标记为流式，使用流式解密路径。
- 如果文件头没有流式标记，按旧版非流式文件处理。
- 如果文件头标记为流式但缺少必要元数据，应返回明确的文件格式错误。

### 5.3 用户感知

用户不需要手动指定是否流式处理。以下命令应自动工作：

```bash
crypto encrypt -i large_video.mp4 -o large_video.mp4.enc
crypto decrypt -i large_video.mp4.enc -o large_video.mp4
```

当启用详细日志时，建议显示当前处理模式：

```text
Mode: streaming
Chunk size: 65536 bytes
Original size: 1073741824 bytes
```

中文环境：

```text
处理模式：流式
分块大小：65536 字节
原始大小：1073741824 字节
```

## 6. CLI 参数需求

第一版必须支持自动判断，不强制新增参数。

建议预留以下参数，但可作为后续迭代：

```bash
--streaming auto|always|never
--streaming-threshold <SIZE>
--no-progress
```

参数语义：

- `auto`：默认行为，按阈值自动判断。
- `always`：只要算法支持，就强制使用流式格式。
- `never`：强制使用非流式格式；如果文件超过安全上限，可以报错提醒用户改用流式。
- `--streaming-threshold`：覆盖默认阈值，支持 `KB`、`MB`、`GB`、`KiB`、`MiB`、`GiB`。
- `--no-progress`：关闭进度条。

如果第一版不实现这些参数，代码结构仍应避免把自动判断逻辑写死在难以扩展的位置。

## 7. 支持算法

第一版必须支持：

- AES-256-GCM 流式加密和解密。
- ChaCha20-Poly1305 流式加密和解密。

第一版可以暂不支持：

- AES-256-CBC-HMAC 流式加密和解密。
- RSA-OAEP-2048 直接流式文件加密。
- RSA-OAEP-4096 直接流式文件加密。
- ECIES-P256 直接流式文件加密。

当用户选择不支持流式的算法处理大文件时，程序必须有明确策略：

- 推荐策略：自动回退到非流式路径，并在 verbose 模式提示原因。
- 更安全策略：超过阈值且算法不支持流式时返回错误，提示用户改用 AES-256-GCM 或 ChaCha20-Poly1305。

第一版应采用推荐策略或更安全策略之一，并在 README 中明确说明。

## 8. 加密文件格式需求

现有文件头只能记录算法、KDF、压缩、IV、原始大小和 metadata，不能可靠区分流式和非流式，也不能保存流式解密需要的分块数量。

必须扩展文件格式，使解密端能自描述地判断处理方式。

### 8.1 文件头字段

文件头必须包含以下流式相关信息：

- 是否为流式格式。
- 流式格式版本。
- 分块大小。
- 总分块数，或能可靠表示流结束的等价机制。
- 原始明文大小。
- 压缩前后大小信息，至少应能支持进度显示和完整性校验。

建议使用现有 `metadata` JSON 字段承载第一版扩展，避免立即提升二进制头版本导致兼容风险。

示例：

```json
{
  "streaming": true,
  "stream_version": 1,
  "chunk_size": 65536,
  "total_chunks": 16384,
  "payload_size": 1074003968
}
```

要求：

- 旧文件没有 `metadata.streaming` 时，视为非流式文件。
- `streaming=true` 时，`chunk_size` 和 `total_chunks` 必须存在且合法。
- `chunk_size` 必须大于 0，且不得超过实现允许的最大分块大小。
- `total_chunks` 必须与原始大小或加密数据结构一致。
- metadata 解析失败时，如果无法判断格式，应返回 `InvalidMetadata` 或更具体的错误。

### 8.2 加密数据区格式

流式加密数据区建议采用以下结构：

```text
[chunk_0_len(u32)][chunk_0_ciphertext_and_tag]
[chunk_1_len(u32)][chunk_1_ciphertext_and_tag]
...
[chunk_n_len(u32)][chunk_n_ciphertext_and_tag]
```

要求：

- 每个分块必须独立认证。
- 每个分块的 nonce 必须唯一。
- 每个分块的 AAD 必须包含 chunk index。
- 建议 AAD 同时包含流式格式版本、算法、原始大小、chunk size 和 final chunk 标记，降低格式混淆风险。
- 解密时必须校验分块长度，拒绝过小、过大或与声明不一致的分块。
- 解密完成后必须检查是否有多余尾部数据；有多余数据时应报错，不能静默忽略。

### 8.3 兼容性

必须满足：

- 新版本可以解密旧版本非流式文件。
- 新版本生成的非流式文件仍按现有格式工作。
- 新版本生成的流式文件可以被同版本或后续版本识别。
- 旧版本读取新流式文件时可以失败，但错误应表现为不支持或格式错误，不能误解密出错误明文。

## 9. 压缩需求

当用户启用压缩并且文件达到流式阈值时，应避免重新把完整压缩结果读入内存。

推荐第一版实现方式：

1. 如果未启用压缩，输入文件直接进入流式加密器。
2. 如果启用压缩，优先使用 `compression::compress_stream` 将输入流接到加密流。
3. 如果现有加密流接口无法直接作为压缩输出 writer，应使用临时文件作为折中方案：先流式压缩到临时文件，再根据临时文件大小进行流式加密。
4. 临时文件必须使用唯一文件名，不能使用固定路径，避免并发命令互相覆盖。
5. 失败时必须清理临时文件。

解密时：

1. 先按文件头选择流式或非流式解密。
2. 如果文件头标记压缩，优先流式解压到输出文件。
3. 如果第一版无法完整串接解密流和解压流，应使用临时文件折中，但不能把完整大文件读入内存。

## 10. 目录加密需求

当前目录加密会先将目录创建为归档数据，再写入临时文件并加密。第一版可以保留该行为，但必须明确以下要求：

- 对临时归档文件执行与普通文件相同的大小判断。
- 大于或等于阈值的归档文件应使用流式加密。
- 解密目录归档时，不应通过 `std::fs::read` 将整个临时明文归档读入内存来判断 magic。
- 应通过读取前几个字节判断是否为 `CRYTAR` 归档。
- 如果是目录归档，第一版可以继续调用现有提取逻辑；如果现有提取逻辑需要完整内存，应在文档和代码注释中标记为后续优化点。

## 11. 进度条需求

### 11.1 显示条件

默认显示条件：

- stdout 或 stderr 是交互式终端时显示。
- 用户未传入 `--no-progress` 时显示。
- 发生 verbose 日志输出时，进度条不能和日志互相覆盖。

不应显示的场景：

- 输出被管道捕获。
- CI 环境默认不显示，除非用户强制开启。
- `--quiet` 或未来等价静默参数启用时不显示。

建议将进度条输出到 stderr，避免污染 stdout 的机器可读输出。

### 11.2 进度内容

进度条至少显示：

- 当前操作：Encrypting 或 Decrypting。
- 当前处理字节数。
- 总字节数。
- 百分比。

推荐显示：

- 当前速度。
- 预计剩余时间。
- 当前文件名。

英文示例：

```text
Encrypting large_video.mp4
[=========================>                        ] 52% (558345748/1073741824 bytes)
```

中文示例：

```text
正在加密 large_video.mp4
[=========================>                        ] 52% (558345748/1073741824 字节)
```

完成时：

```text
[==================================================] 100% (1073741824/1073741824 bytes)
```

### 11.3 更新频率

进度条更新应限制频率，避免高频刷新影响性能。

要求：

- 每处理一定字节数或每隔一定时间刷新一次。
- 建议最小刷新间隔为 100ms。
- 完成时必须刷新到 100% 并换行。
- 发生错误时必须换行后输出错误，避免错误信息和进度条在同一行混杂。

### 11.4 进度基准

加密未压缩文件：

- 进度基准使用原始文件大小。
- 每读取一个明文分块后更新进度。

加密压缩文件：

- 如果压缩和加密串接，进度基准优先使用原始输入读取字节数。
- 如果先压缩到临时文件，再加密临时文件，需要分别显示压缩阶段和加密阶段，或显示总体阶段标签。

解密未压缩文件：

- 进度基准可以使用密文 payload 大小或原始明文大小。
- 推荐使用密文 payload 已读取字节数，因为这是解密过程天然可观测的进度。

解密压缩文件：

- 解密阶段和解压阶段应分别显示，或显示统一阶段但不能倒退。

## 12. 错误处理需求

必须处理以下错误：

- 输入文件不存在。
- 无法读取输入文件 metadata。
- 输入文件大小超过平台可处理范围。
- 流式 metadata 缺失或非法。
- 分块长度非法。
- 分块认证失败。
- 文件提前结束。
- 文件存在多余尾部数据。
- 输出文件写入失败。
- 临时文件创建失败。
- 临时文件清理失败。
- 用户选择的算法不支持流式处理。

错误信息要求：

- 中文环境输出中文错误。
- 英文环境输出英文错误。
- 错误信息应说明失败阶段，例如读取、加密、解密、认证、写入或清理。
- 认证失败必须停止处理，并删除未提交的临时输出文件。

## 13. 安全需求

- 每个流式分块必须使用唯一 nonce。
- nonce 派生不得在同一 key 和同一 base nonce 下重复。
- 分块 AAD 必须至少绑定 chunk index。
- 推荐绑定更多上下文：算法、格式版本、chunk size、original size、final chunk。
- 解密时必须按顺序处理分块，不能允许重排。
- 解密失败时不能留下看似成功的输出文件。
- 所有密钥和密码仍应使用现有 `SecureBytes` 清零策略。
- 进度条不得输出密钥、密码、salt、IV 或其他敏感材料。

## 14. 性能需求

目标：

- 大文件加密、解密内存占用应近似恒定。
- 未压缩大文件的主数据路径不得使用 `read_to_end` 或 `std::fs::read` 读取完整文件。
- 单个分块缓冲区建议继续使用 `64 KiB`。
- 实际峰值内存应主要由输入缓冲区、输出缓冲区、认证缓冲区和少量 metadata 构成。

验收建议：

- 使用至少 256 MiB 的测试文件验证流程。
- 使用至少 1 GiB 的手工测试文件验证进度条和内存占用。
- 大文件处理期间内存占用不应随文件大小线性增长。

## 15. 测试需求

### 15.1 单元测试

必须新增或更新以下测试：

- 小文件加密仍使用非流式格式。
- 大文件加密自动使用流式格式。
- 流式文件头包含必要 metadata。
- 流式 AES-256-GCM 往返成功。
- 流式 ChaCha20-Poly1305 往返成功。
- 流式文件分块认证失败时解密失败。
- 流式文件截断时解密失败。
- 流式文件追加多余数据时解密失败。
- 旧版非流式文件仍可解密。
- metadata 缺失或非法时返回明确错误。

### 15.2 集成测试

必须覆盖 CLI 层：

```bash
crypto encrypt -i large.bin -o large.bin.enc
crypto decrypt -i large.bin.enc -o large.bin.out
```

验收：

- `large.bin.out` 与 `large.bin` 字节完全一致。
- verbose 模式显示流式处理模式。
- 进度条能到达 100%。
- 非交互输出场景不污染 stdout。

### 15.3 目录测试

必须覆盖：

- 大目录归档文件达到阈值后使用流式加密。
- 解密目录归档时不通过完整读取临时明文判断 magic。
- 解密后的目录结构、文件内容和基础 metadata 与原目录一致。

### 15.4 压缩测试

必须覆盖：

- 大文件 + gzip 压缩 + 流式加密 + 解密恢复。
- 大文件 + zstd 压缩 + 流式加密 + 解密恢复。
- 压缩阶段失败时临时文件被清理。
- 解压阶段失败时输出文件不被提交。

## 16. 文档需求

实现完成后必须更新：

- `README.md` 的大文件加密说明。
- `README.md` 的性能特性说明。
- `README.md` 的加密文件格式说明。
- `crypto info` 输出说明，展示是否为流式文件、chunk size、total chunks。
- 命令帮助信息，如果新增 `--streaming`、`--streaming-threshold` 或 `--no-progress` 参数。

如果第一版没有实现某些高级能力，README 不能继续笼统声称所有大文件都恒定内存处理。

`crypto info -i <file>` 应展示流式相关信息。

非流式文件示例：

```text
Streaming: No
```

流式文件示例：

```text

Stream Version: 1
Chunk Size: 65536 bytes
Total Chunks: 16384
```

中文环境：

```text
是否流式：是
流式格式版本：1

```

## 18. 实现约束

- 自动判断逻辑应位于 `file_handler` 或更靠近文件处理边界的位置。
- `app.rs` 不应复制复杂的流式判断逻辑。
- 流式和非流式路径应共享文件头读写、KDF、算法选择和错误处理逻辑。
- 进度回调应作为可选参数传递，避免底层 crypto 模块直接依赖 CLI 输出。
- `crypto.rs` 应继续保持纯加密逻辑，不直接打印进度条。
- 不应使用固定名称临时文件，例如 `crypto_cli_decrypted.tmp` 或 `crypto_cli_archive.tmp`，处理大文件时尤其需要避免并发冲突。
- 不应在大文件路径中使用 `read_to_end`、`std::fs::read` 或等价全量读入。

## 19. 验收标准

本需求完成后，应满足以下条件：

- 加密大于等于阈值的 AES-256-GCM 文件时，自动写出流式格式。
- 加密大于等于阈值的 ChaCha20-Poly1305 文件时，自动写出流式格式。
- 解密流式文件时，自动使用流式解密，不依赖用户参数。
- 解密旧版非流式文件仍成功。
- 加密和解密过程中显示进度条，并能正常完成到 100%。
- 非交互输出场景不会污染 stdout。
- 大文件加密、解密过程内存占用不随文件大小线性增长。
- 认证失败、截断、追加尾部数据都能被检测。
- 临时输出文件在失败时被清理。
- README 与实际行为一致。

## 20. 建议实施顺序

1. 扩展文件头 metadata，定义流式 metadata 结构。
2. 增加文件大小判断和流式策略类型。
3. 将 `file_handler::encrypt_file` 拆分为非流式路径和流式路径。
4. 将 `file_handler::decrypt_file` 改为按文件头选择路径。
5. 增加进度回调接口，并让 CLI 层负责渲染进度条。
6. 修复目录解密中完整读取临时明文判断归档 magic 的问题。
7. 处理压缩场景，至少避免大文件全量读入内存。
8. 增加单元测试和 CLI 集成测试。
9. 更新 README 和命令帮助。
